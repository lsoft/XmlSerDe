# Changelog

## 0.1.0-alpha.1 — unreleased

The first package. Everything below happened **before** it, while the library existed only as source, so none of it can break a version you already have — there is none. It is kept because the decisions are the interesting part: each entry says what changed and, more usefully, why, and several of them are the reasons the current API looks the way it does.

If you are reading this to find out what XmlSerDe does today, read the [README](README.md) instead; this file is history.

**Breaking change (namespaces).** The three `using` directives a serializer file needed — `XmlSerDe.Common`, `XmlSerDe.Components.Exhauster`, `XmlSerDe.Components.Injector` — are now one: `using XmlSerDe;`. Those names described how the library is cut into assemblies, which is not something a consumer should have to know or type. The assembly names are unchanged; only the namespaces moved, and the parser internals moved further, to `XmlSerDe.Internal`. See [Namespaces](#namespaces) for what that split promises and what it doesn't. This is deliberately done before the first package: a namespace rename afterwards is a source break in every file of every consumer, and a type-forward does not help, because a type-forward is about assemblies.

**New guard `XmlGuard.ForeignRootNamespace`, and a behaviour change in drop-in mode.** There was exactly one input on which XmlSerDe **accepted** what `System.Xml.Serialization` refuses: a document whose root declares a default namespace (`<Order xmlns="urn:acme:orders">`). Names are compared as literal text, `xmlns` was just another unrecognised attribute, so someone else's vocabulary was read as yours and the result was a filled object rather than an error. The new guard rejects it; `XmlSerDe.Compat` has it on, since it is part of `SystemXmlCompatible`, so the facade now throws where it used to return an object. The native default is unchanged and pays nothing — the check is generated only for a host that asks for it, runs on the root alone, and ignores the `xmlns:xsi` / `xmlns:xsd` declarations the BCL writes on every document. What it does not see is a declaration below the root; that limit is stated in [Opt-in XML guards](#opt-in-xml-guards).

**Breaking change (non-public members).** An `internal`, `protected internal` or `private protected` member was being serialized; it no longer is. Only `public` members take part now, which is what `System.Xml.Serialization` has always done — it collects members with `BindingFlags.Public`. If your documents currently carry such an element, it will silently disappear from them, so this is worth grepping for before you upgrade. In drop-in mode the same quirk was costing you the acceleration outright: the facade compares its member set against the BCL's and refused any type where the two disagreed, so a single `internal` property sent the whole type back to `System.Xml.Serialization`.

**Generated code no longer warns in your build.** Every generated file now opens with `// <auto-generated/>` and `#pragma warning disable`. Measured on an empty consumer project: `GenerateDocumentationFile` produced 654 `CS1591` from generated sources and the `roschar` alias 20 `CS8981` — and with `TreatWarningsAsErrors`, which is on by default in many templates, either number meant the project did not build at all, over code the consumer never wrote and cannot edit. The suppression is deliberately blanket rather than a list of codes: a list only covers the warnings we thought of, and it is the consumer who decides which ones are on. Our own signal is kept by a test that compiles the same code with the prelude stripped and fails on any warning outside a named set.

**Breaking change (native path):** a `[XmlSubject]` serializer without `[XmlFeatures]` no longer reads comments, CDATA, processing instructions, DOCTYPE, single-quoted attributes, `>` inside attribute values, or a non-`xsi` prefix for `xsi:type` / `xsi:nil`, and string serialization no longer runs `XmlCharGuard`. That is the fast POCO path. To get the previous native behaviour:

```csharp
[XmlFeatures(XmlFeature.SystemXmlCompatible)]
[XmlSubject(typeof(Order), true)]
public partial class OrderSerializer { }
```

`XmlSerDe.Compat` turns those features on by itself; user code does not add the attribute. See [Opt-in XML features](#opt-in-xml-features).

Two smaller breaks come with it: a custom `IExhauster` now also implements `AppendEncodedUnchecked` / `AppendAttributeEncodedUnchecked` (the unguarded pair the default path calls), and `BuiltinCodeHelper.CutXmlHead(span)` alone no longer skips comments, PIs or a DOCTYPE — call the generated `YourSerializer.CutXmlHead(span)`, which passes that host's own flags.

`XmlFeature` itself was then cut from seven flags to four. `QuotedAttributes` is gone and its behaviour is unconditional; `Comments`, `ProcessingInstructions` and `Doctype` are gone and folded into a single `Markup`, which `CData` now includes. `SystemXmlCompatible` is unchanged in meaning. The reasoning, with numbers, is in [Cost of turning a flag on](#cost-of-turning-a-flag-on).

**Breaking change (attribute syntax, every host):** a broken attribute head is now an error instead of a wrong object. `<Foo id=1 Tag="x">` used to read as `id="x"` — the value stolen from the neighbouring attribute, `Tag` lost — and `<Foo id Tag="x">` used to produce an attribute named `"id Tag"` that matched nothing. Both now throw. This is not a flag: there is no mode in which reading the neighbour's value is correct. The same check repairs the mirror bug on **valid** input — `<Foo a = "1">` is legal XML that used to be dropped silently, because the attribute name ended only at `=`, `:`, `/` or `>`.

**Breaking change (drop-in):** `XmlSerDe.Compat` now refuses malformed documents the way `System.Xml.Serialization` refuses them — a second root element, a duplicate attribute, a mismatched or missing closing tag, an illegal `Char` in a string. Code that relied on the facade quietly accepting broken input will start seeing `InvalidOperationException` → `XmlException`, which is what the BCL raised there all along. The native path is unaffected unless you ask for it with `[XmlGuards]` — see [Opt-in XML guards](#opt-in-xml-guards).

**Breaking change (custom injector):** `IInjector.Parse` lost its `xmlnsAttributeName` parameter; the value now rides inside the parse context, together with everything else contextual. `XmlNode2`'s public constructor and `XmlNode2.GetFirst` lost the same parameter for the same reason. A caller that passed `roschar.Empty` simply drops the argument; a caller that had a real name passes `context.WithXmlnsAttributeName(name)` instead. `XmlDeserializeSettings` is renamed to `XmlParseContext` to match what it now carries — parse state, not just settings. The point is not the parameter itself but the shape: a context that is one `ref` struct grows by adding a field, and a field breaks nobody, whereas that parameter broke all 33 `Parse` overloads at once.

**Breaking change (custom sinks):** a custom exhauster now derives from `XmlSerDe.ExhausterBase` and a custom injector from `XmlSerDe.InjectorBase`; implementing `IExhauster` / `IInjector` alone is no longer accepted, and the generator says so. The interfaces stay — the base classes implement them — but the contract the generator checks is the class. The reason is the two breaking changes above: on an interface, every added member breaks every implementer at once, by source and by binary alike. On a class a new member arrives `virtual` with a default body and nobody notices. That rule is now written into the bases and is the point of the change: **a new member is only ever added as `virtual` with a working default**, expressed through `Append(string?)` / `ParseBody`. Shipped exhausters change only their base type; `DefaultInjector` still works as the base for a custom injector, except its methods are now `override` rather than `new`. Details in [docs/sink-contract.md](docs/sink-contract.md).

The generator also gained `XMLSERDE010`, a warning when the type named in `[XmlExhauster]` / `[XmlInjector]` is not `sealed`: the generated call is made on the concrete type, so a sealed one devirtualizes to exactly the cost of a non-virtual method and an open one does not. Measured in [docs/dispatch-cost.md](docs/dispatch-cost.md): on a real sink the difference stays inside the noise floor, on a degenerate one it is 5x, and a polymorphic call site costs 1.2-1.8x.

**Behaviour changes (code review, September 2026).** Each of these is a case where the output differed from `System.Xml.Serialization` on the same input; every one is pinned by a test that runs the BCL alongside.

- *Parser.* Element text is normalized per XML 1.0 §2.11: CRLF and a lone CR become LF before the value reaches the injector (a CR that arrives as `&#13;` stays). A comment inside element text on a `Markup` host no longer ends the text: `<S>hello<!-- c -->world</S>` reads `helloworld`; before, everything in front of the comment was dropped. `</Name >` with whitespace before `>` is accepted (§3.1).
- *Generator.* A member hidden with `new` is taken once, from the most-derived type, in the base member's slot. `readonly` fields and `init`-only properties are skipped unless they are a `List<T>` filled through `Add` (see [Limitations](#limitations)). `[XmlInclude]` is transitive — a leaf declared on an intermediate type is visible to the base — and dispatch tests the most-derived type first, so a leaf no longer goes out under its parent's `xsi:type`. Two derived types that would share an `xsi:type` name (same simple name, different namespaces) are a generator error, as they are in the BCL. `[XmlArrayItem("name")]` on a collection of a complex type reads back. `<string />` and `<Item />` inside a collection are read as an empty value and a default object rather than dropped; `<string xsi:nil="true" />` reads as `null`. A member named with a C# keyword (`@class`) and a negative enum `[DefaultValue]` now compile. So do the remaining `[DefaultValue]` shapes that used to emit code the compiler rejected: `NaN` and `±Infinity` were written into the source as the words `ToString()` gives them, which are not C# literals (CS0103), and a value whose type does not match the member's — `[DefaultValue(1)]` on an enum member, `[DefaultValue(true)]` on an `int` one — was compared with `!=` regardless (CS0019). A number against an enum member is now cast to the enum, which is what the BCL matches on; a genuinely incomparable value produces no guard at all, so the member is always written, which is also what the BCL does. Generated code for every other type is unchanged, byte for byte. Generated files are named by the host's full name (`Ns.Host.g.cs`), so two hosts with the same simple name in different namespaces both get their code; before, the second was silently skipped. A setter-less `Dictionary<K,V>` property is skipped instead of crashing the generator.
- *Sinks.* The attribute encoder writes runs between escapable characters instead of one character at a time; as a side effect a surrogate pair that follows `<`, `>`, `&`, `"`, TAB, CR or LF in an attribute value is no longer split into two U+FFFD on the UTF-8 sinks. `LengthEstimatorExhauster` now returns the exact encoded length (it did not count `&quot;`, Latin-1 160–255 or supplementary-plane characters, so the pooled second pass regrew and copied on non-English text). `Utf8StreamExhauster` is `sealed`. Numbers, dates and GUIDs on the UTF-8 sinks are formatted straight into bytes on .NET 8+.
- *Drop-in.* A call through a base-typed reference now really goes out through `WriteRaw`: the base class injects the default `xsi`/`xsd` namespaces when the caller passed none, and the facade mistook them for caller-supplied ones and fell back to the BCL on every such call. `Serialize(TextWriter)` and `Serialize(Stream)` flush the sink like the BCL does. `Deserialize(Stream)` decodes by BOM, UTF-16 byte order and the declared `encoding`, and rejects invalid UTF-8, like `XmlTextReader`. A root `<T xsi:nil="true"></T>` is `null`.
