# Opt-in XML-фичи ядра: задача и требования к реализации

**Статус:** реализовано (2026-08-26), набор флагов сокращён с семи до четырёх по результатам замера (2026-09-04). Требования ниже переписаны только там, где они описывают текущее поведение; чем код разошёлся с исходным текстом — в [§16](#16-расхождения-с-этим-документом), почему флагов стало меньше — в [§17](#17-свёртка-набора-флагов-после-замера).
**Связанные документы:** [README — Out of scope by design](../README.md#out-of-scope-by-design), [perf-single-pass-parser.md](perf-single-pass-parser.md), [xmlserializer-compat.md](xmlserializer-compat.md), [opt-in-xml-guards.md](opt-in-xml-guards.md) (ортогонально: well-formedness на входе, не XML-фичи).

Документ самодостаточный: по нему должно быть можно реализовать работу, не поднимая переписку.

## 1. Задача

Ядро XmlSerDe — это **POCO ↔ XML data binding**, а не универсальный XML-процессор. Ряд XML 1.0-фич, которые сейчас всегда включены в горячем пути, для этого сценария почти не нужны: XmlSerDe их сам не пишет, `System.Xml.Serialization` (для поддерживаемого подмножества) — тоже.

Требуется:

1. **По умолчанию** native-путь (`[XmlSubject]` без дополнительных атрибутов) генерирует и исполняет код **без** этих фич.
2. Пользователь **включает** нужные фичи атрибутом с `[Flags]`-перечислением на классе-сериализаторе. Генератор тогда порождает код, который фичу понимает.
3. **Compat-слой** включает у себя **все** фичи, нужные чтобы читать и писать то, что читает и пишет `System.Xml.Serialization`, **автоматически**, без атрибута на пользовательском коде.

Совместимость native-пути с compat-слоем при выключенных фичах **не является** ограничением этой задачи: native без флагов имеет право отказаться понимать документ, который compat всё ещё примет.

Это **breaking change** native-пути. Поведение с явным «включить всё» должно совпасть с сегодняшним.

## 2. Зачем

Замеры на net10.0 (Release; десериализация POCO-документа, который пишет сам XmlSerDe, ≈ 2.16 µs; DEEP ≈ 4.17 µs; сериализация REGULAR ≈ 1.52 µs). Цифры — порядок величины на конкретной машине; после реализации их надо переснять и вписать в README, а не копировать слепо.

| Фича, которая сейчас всегда на горячем пути | Нужна ли типичному POCO | Где платится | Оценка выигрыша, если выключить |
|---|---|---|---|
| Комментарии, CDATA, PI, DOCTYPE + **два эвристических `IndexOf` по всему документу** до разбора | Нет: ни XmlSerDe, ни BCL их не пишут (кроме `<?xml …?>` в прологе, который снимает опциональный `CutXmlHead`) | Каждый корневой `Deserialize` | **~6%** POCO REGULAR, **~4–6%** DEEP. Основной кусок — эвристики (125–160 ns), а не сам разбор CDATA |
| `XmlCharGuard` (Char production XML 1.0 §2.2) на каждой строке при сериализации | Нет: обычные POCO-строки легальны | `AppendEncoded` / `XmlAttributeEncoder` | **~6%** сериализации REGULAR, линейно с длиной строк |
| Quote-aware поиск `>` в голове и одинарные кавычки атрибутов | Нет: оба писателя экранируют `>` и пишут `"` | `ScanHead` / `FindUnquotedGt` / разбор атрибута | **~3%** REGULAR с несколькими атрибутированными элементами, **0%** DEEP |
| Гибкий префикс `xsi` (поиск `xmlns:*=XMLSchema-instance`) | Нет для interop с BCL/XmlSerDe: оба пишут `xsi`. Тесты ядра часто используют `p3` | `ReadHead` + `GetPreciseNodeType` | **~3–6%** REGULAR с полиморфизмом, **0%** DEEP |

Что в этот список **не** входит и выключать **нельзя**: предопределённые сущности и CharRef (`&amp;`, `&#39;`, …), `xsi:type` / `xsi:nil` как таковые, коллекции, `S`-production пробелов между элементами. Это формат POCO, а не «лишняя XML-фича».

Отдельно: эвристики `IsXmlCommentExistsHeuristic` / `IsCDataBlockExistsHeuristic` при compile-time флаге **не нужны ни во включённом, ни в выключенном виде**. Сейчас они сканируют весь документ, чтобы решить, смотреть ли на комментарии/CDATA; генератор и так знает ответ. На DEEP эвристики — чистый убыток (скан ~160 ns, чтобы не делать ~6 ns работы). После этой задачи их **не должно быть** в сгенерированном `Deserialize`.

Ещё один факт, который нельзя перепутать с выигрышем от выключения: документ **с** CDATA сейчас разбирается *быстрее* эквивалента через сущности (сырое копирование секции дешевле раскрытия `&amp;`/`&lt;`). Выключение CDATA ускоряет **POCO-вход без CDATA**, а не текущий `ComplexFixture.AuxXml`. Официальный REGULAR-бенчмарк после задачи должен мерить **default-путь** (см. §11).

## 3. Публичный API

### 3.1. Перечисление

В `XmlSerDe.Common`, `[Flags]`, имя `XmlFeature` (единственное число, как у типичных flag-enum).

Каждый член — **отдельно включаемая фича**, которую пользователь узнаёт по XML, а не по имени метода в `XmlScan`. Генератор имеет право внутри схлопывать несколько флагов в один специализированный метод, если это не меняет наблюдаемое поведение.

```csharp
[Flags]
public enum XmlFeature
{
    None = 0,

    /// <summary>
    /// Разметка между элементами и в прологе: комментарии
    /// <c>&lt;!-- ... --&gt;</c>, processing instructions <c>&lt;?...?&gt;</c>
    /// и <c>&lt;!DOCTYPE ...&gt;</c>. Без флага любая из них — ошибка разбора,
    /// а не «пропустить». XML-декларация к разметке не относится: её
    /// по-прежнему снимает только явный вызов <c>CutXmlHead</c>.
    /// </summary>
    Markup = 1 << 0,

    /// <summary>
    /// Секции CDATA: в тексте элемента разворачиваются в значение, между
    /// элементами пропускаются. Включает в себя <c>Markup</c>.
    /// Без флага литеральный <c>&lt;</c> в теле — ошибка,
    /// <c>&lt;![CDATA[</c> не распознаётся.
    /// </summary>
    CData = Markup | (1 << 1),

    /// <summary>
    /// Префикс <c>xsi</c> не зашит: ищется <c>xmlns:*=http://www.w3.org/2001/XMLSchema-instance</c>,
    /// и <c>type</c>/<c>nil</c> читаются с этим префиксом.
    /// Без флага значащие имена — литералы <c>xsi:type</c> и <c>xsi:nil</c>.
    /// </summary>
    FlexibleXsiPrefix = 1 << 2,

    /// <summary>
    /// Перед экранированием строки на сериализации — <see cref="XmlCharGuard"/>
    /// (запрещённые XML 1.0 §2.2 символы → <c>ArgumentException</c>).
    /// Без флага нелегальный символ может оказаться в выходном XML.
    /// </summary>
    CharGuard = 1 << 3,

    /// <summary>
    /// Набор, достаточный чтобы native-сериализатор понимал те же входные
    /// конструкции, что <c>System.Xml.Serialization.XmlSerializer</c> на
    /// поддерживаемом подмножестве типов. Это же значение автоматически
    /// получает compat-слой.
    /// </summary>
    SystemXmlCompatible =
        CData
        | FlexibleXsiPrefix
        | CharGuard,
}
```

Изначально флагов было семь: `Comments`, `CData`, `ProcessingInstructions`, `Doctype`, `QuotedAttributes`, `FlexibleXsiPrefix`, `CharGuard`, и этот раздел требовал держать их раздельно даже там, где код общий. После реализации и замера требование снято — почему именно, см. §17. Правило «добавлять новые члены нельзя без правки этого документа» остаётся в силе.

Флаг заводится под свою цену. Если две конструкции исполняются одним и тем же кодом, разделять их незачем: замер показывает, что цена входа на разметочный путь ~15% разбора, а какие именно конструкции на нём распознаются — в пределах шума. `CData` — исключение: у неё есть собственная цена помимо входа (разворачивание в текст и обход `IInjector`), поэтому она осталась отдельным членом, но включает в себя `Markup`.

Составной член требует от кода проверки по полной маске: `(features & flag) == flag`, а не `!= 0`. Проверка «хоть один бит совпал» объявила бы `CData` у любого хоста с `Markup`.

`XmlFeature.None` и отсутствие атрибута — одно и то же.

### 3.2. Атрибут

Новый атрибут на **классе-сериализаторе** (там же, где `[XmlSubject]`, `[XmlExhauster]`, `[XmlInjector]`, `[XmlFactory]`), не на каждом subject-типе: фичи — свойство разбора/записи документа, общее для всех типов хоста.

```csharp
[AttributeUsage(AttributeTargets.Class, AllowMultiple = true)]
public sealed class XmlFeaturesAttribute : Attribute
{
    public XmlFeature Features { get; }

    public XmlFeaturesAttribute(XmlFeature features)
    {
        Features = features;
    }
}
```

Правила:

- Несколько атрибутов на одном классе **объединяются через OR**. `[XmlFeatures(XmlFeature.CData)]` + `[XmlFeatures(XmlFeature.Comments)]` ≡ `CData | Comments`.
- Атрибут на subject-типе, члене, сборке — не читается и не диагностируется в рамках этой задачи (как сейчас не читается `[XmlSubject]` не на хосте).
- Неизвестный комбинации нет: это flags.
- Пустой `[XmlFeatures(XmlFeature.None)]` допустим и равен отсутствию атрибута.

Не расширять `[XmlSubject]`: у него уже два позиционных аргумента, и фичи не про конкретный тип.

### 3.3. Compat

Сгенерированный `XmlSerDeCompatSerializer` получает `XmlFeature.SystemXmlCompatible` **внутри генератора**, без требования к пользовательскому коду и без необходимости писать `[XmlFeatures]` рядом с `new XmlSerializer(typeof(T))`.

Пользовательский `[XmlSubject]`-класс в той же сборке, что и compat, **не** наследует эти флаги. Иначе подключение `XmlSerDe.Compat` «для одного типа» внезапно замедлило бы native-сериализаторы — прямое нарушение правила «не используешь drop-in — не платишь» из [xmlserializer-compat.md](xmlserializer-compat.md).

Если в сборке есть и `[XmlSubject]`-хост без флагов, и compat-точки вызова — порождаются **два** разных набора методов (как сейчас два разных класса), с разным набором фич.

### 3.4. Что не является API этой задачи

- Runtime-переключатель на `Deserialize(...)` / `XmlDeserializeSettings`. Фича выбирается **на этапе генерации**. Передавать в сгенерированный `ReadHead` два `bool` «на всякий случай», как сейчас, нельзя: `ReadHead` эти bool и так игнорирует, а `SkipToTag` всегда смотрит на `<!`/`<?`.
- Конфигурация MSBuild (`XmlSerDeFeatures=...`) — не требуется. Если позже понадобится, это отдельная задача; сейчас только атрибут.
- Включение фич «на один вызов».

## 4. Контракт генератора

### 4.1. Default (нет атрибута / `None`)

Сгенерированный код **не содержит** и **не вызывает**:

- `XmlNode2.IsXmlCommentExistsHeuristic`
- `XmlNode2.IsCDataBlockExistsHeuristic`
- `XmlNode2.GetLeadingCommentLengthIfExists`
- ветки CDATA в `ReadTextBody` / `XmlTextDecoder.DecodeElementText`
- `XmlScan.FindUnquotedGt` (голова закрывается первым `>` после имени / после атрибутов без учёта кавычек — см. §5.3)
- поиск атрибутной кавычки `'`
- поиск `xmlns` с URI `XMLSchema-instance` для открытия префикса
- `XmlCharGuard.EnsureValidXmlChars`

Допустимо, чтобы эти методы **жили** в `XmlSerDe.Common` для opt-in пути и для публичного `XmlNode2`. Default-хост просто на них не ссылается. Тест по сгенерированному тексту это проверяет (см. §10.2).

Корневой `Deserialize` **не** строит `XmlDeserializeSettings` из эвристик. Если `settings` ещё нужен `IInjector.Parse` (старый путь через `XmlNode2`), в default он создаётся как «все эвристики ложь» **без скана документа**, либо `Parse`/`XmlNode2` переводятся на тот же compile-time набор фич. Предпочтительный вариант — сгенерированный hot path по-прежнему идёт в `ParseBody` + `XmlScan.ReadTextBody`, а не в `XmlNode2.GetFirst`.

### 4.2. Opt-in

Для каждого включённого флага генератор вызывает **специализированные** примитивы, которые фичу реализуют. Не передавать `true` в метод, который при `false` всё равно делает ту же работу.

Минимальная схема специализации (имена — ориентир, не обязательный контракт):

| Флаг | Default-примитив | Opt-in-примитив |
|---|---|---|
| `Comments`, `CData`, `ProcessingInstructions`, `Doctype` | `ReadHead` / `SkipToTag` без ветки `<!`/`<?`; `ReadTextBody` без CDATA и без ведущих комментариев; `DecodeElementText` ищет только `&` | варианты, которые пропускают/разбирают только **включённые** конструкции; выключенная конструкция в той же позиции — ошибка |
| `QuotedAttributes` | `ScanHead`: конец головы = `IndexOf('>')` от конца имени; атрибут только `"..."` | текущие `FindUnquotedGt` + `IndexOfAny('"', '\'')` |
| `FlexibleXsiPrefix` | `xsi:type` / `xsi:nil` как литеральный префикс `xsi` | текущий разбор xmlns-URI и наследование префикса |
| `CharGuard` | экранирование строки без `EnsureValidXmlChars` | как сейчас, guard до encode |

Генератор **не** генерирует тела `XmlScan` в каждый хост: примитивы остаются в `XmlSerDe.Common`, хост только выбирает, какую перегрузку звать. Иначе два хоста с разными флагами в одной сборке начнут дублировать сканер.

`BuiltinCodeHelper` — partial на всю сборку. Он **не** должен стать «общим знаменателем с максимальным набором фич»: тогда native-хост без флагов заплатил бы за compat. Либо helper остаётся безфичевым (экран/парс builtin-лексем, `CutXmlHead` — см. §5.6), а фичезависимые вызовы живут в коде хоста; либо helper получает суффиксные методы (`DecodeElementText` / `DecodeElementTextWithCData`) и хост выбирает имя.

### 4.3. Несколько хостов в одной сборке

Хост A без флагов и хост B с `CData` должны сосуществовать. Поведение A не меняется от наличия B. Это уже так для разных `[XmlSubject]`-классов; новый атрибут не должен сломать инвариант.

Compat-класс в той же сборке — третий хост с `SystemXmlCompatible`.

### 4.4. Инкрементальность

Флаги — часть входа генератора. Правка `[XmlFeatures]` на хосте обязана давать `IncrementalStepRunReason.New` / не-`Cached` на шаге `Generate`. Правка комментария в файле хоста по-прежнему `Cached`, если сгенерированный текст не изменился.

`GenerationResult` сравнивается по строкам: различный набор фич обязан давать различный текст (разные имена методов или литералы). Нельзя генерировать одинаковый текст и «выбирать фичу в рантайме» — это обход задачи.

### 4.5. Структура генератора: не лапша из `if`

`ClassSourceProducer` уже большой: цикл по членам, коллекции, полиморфизм, атрибуты, `[XmlText]`. Фичи из §3.1 ортогональны этой логике. Если в каждый `GenerateDeserializeMember` / `GenerateSerialize*` / `GenerateReadTextBodyStatement` добавить `if (_features.HasFlag(CData))` — генератор станет нечитаемым, а следующая фича вставится в десяток мест и разъедется.

Это **требование**, не совет.

**Запрещено**

- Размазывать `HasFlag` / `switch (features)` по методам, которые строят граф типа (члены, коллекции, `xsi:type` диспетчер, имена элементов). Там фич нет.
- Копировать целые шаблоны `DeserializeBody` «с CDATA» и «без CDATA». Шаблон один.
- Эмитить в сгенерированный код лестницу `if (comments) … else if (cdata) …`. Хост вызывает уже выбранный примитив; развилки фич в `{ClassName}.g.cs` быть не должно, кроме тех, что и сейчас есть (имя члена, `IsBodyless`, полиморфный тип).
- Порождать по комбинации флагов отдельный клон сканера (7 флагов → до 128 методов `ReadHead_Comments_CData_…`). Комбинаторный взрыв в `XmlScan` — та же лапша, только в Common.

**Обязательно**

Один объект привязки, собирается **один раз** при создании producer (из OR атрибутов хоста или из `SystemXmlCompatible` у compat) и дальше только читается.

Имена — ориентир: `HostFeatureBinding` / `FeatureEmission`. Поля — строки (или `nameof`) тех примитивов, которые этот хост зовёт:

```
ReadHead
ReadTextBody
DecodeElementText          // если хост зовёт декодер напрямую; иначе это внутри ReadTextBody
ScanHead / FindUnquotedGt  // обычно внутри ReadHead, наружу не торчит
GetPreciseNodeType / IsNil
Encode / EncodeChecked     // сериализация строк
CutXmlHead
```

Все интерполяции в `ClassSourceProducer` используют `binding.ReadHead`, не пересчитывают флаги. Образец уже есть: `GenerateReadTextBodyStatement` — одно место, откуда торчит вызов `ReadTextBody`. Его и расширять; не плодить второй такой helper с `if`.

**Уточнение по факту реализации.** У одного call site ось оказалась не одна. Доступ к `xsi:type` выбирается и по `FlexibleXsiPrefix`, и по тому, есть ли у типа наследники: у типа без наследников атрибут ничего не диспетчеризует, в документах его обычно нет, и перед разбором окупается отрицательный фильтр `IndexOf("xsi:type")` (замер — README, «Cost of the `xsi:type` lookup»: ×0.84 на атрибутном POCO). Вторая ось — не фича хоста, а факт про граф типов, поэтому она приходит **параметром** (`binding.PreciseNodeTypeAccessor(hasDerived)`), а не читается из флагов. Правило §4.5 при этом соблюдено: выбор имени по-прежнему живёт в binding, `ClassSourceProducer` подставляет результат и сам ни одного флага не проверяет. Поле `GetPreciseNodeType` осталось для остальных call site, где тип заведомо полиморфный, и юнит стережёт, чтобы поле и метод не разъехались.

Таблица «флаги → binding» живёт в **одном** чистом методе/типе, без `Compilation` и без Roslyn. Её можно (и нужно) тестировать юнитом: набор флагов → ожидаемые имена методов. Тогда регрессия «CData включили, а хост всё ещё зовёт Decode без CDATA» ловится без `CSharpGeneratorDriver`.

Независимые оси **не** перемножаются:

| Ось | Сколько входных точек в Common | Кто выбирает |
|---|---|---|
| разметка между элементами (Comments, CData, PI, Doctype) | две: `ReadHead` без ветки `<!`/`<?`, и `ReadHeadMarkup` | binding: default, если все четыре выключены; иначе markup |
| CDATA / ведущий комментарий в теле | две–четыре перегрузки `ReadTextBody` **или** одна markup-перегрузка, которой binding передаёт только включённые виды (см. ниже) | binding |
| `QuotedAttributes` | две: простой `>` / только `"`, и текущий `FindUnquotedGt` | внутри `ReadHead` той оси, которую уже выбрали, либо две реализации `ScanHead`, которые `ReadHead*` зовут сами. Генератор про кавычки **не** знает, если это спрятано в `ReadHead`/`ReadHeadQuoted` |
| `FlexibleXsiPrefix` | две реализации `GetPreciseNodeType` / `IsNil` / поиска xmlns | binding на тех call site, где хост сам зовёт type/nil |
| `CharGuard` | два helper encode | binding на serialize-call-site строк |

Если `QuotedAttributes` и markup ортогональны внутри `ReadHead`, **не** делать `ReadHead`, `ReadHeadMarkup`, `ReadHeadQuoted`, `ReadHeadMarkupQuoted` четырьмя публичными методами, которые выбирает генератор. Спрятать кавычки за параметром, который **не** идёт из хоста, а зашит в две реализации `ScanHead`, вызываемые из `ReadHead*`. Генератор выбирает только то, что реально пишет в `.g.cs`. Чем короче binding, тем меньше мест в producer.

Допустимое исключение из «никаких `if` по флагам в рантайме»: метод `ReadHeadMarkup` / `SkipNonElementMarkup`, который **уже** сработал на `<!` или `<?` (это не POCO-hot-path). Там можно разобрать, какая это конструкция, и отвергнуть её, если соответствующий флаг выключен. Это лучше, чем 16 клонов `SkipToTag`. На default-пути этого метода нет.

**Как выглядит сгенерированный `DeserializeBody`**

Как сегодня: цикл `ReadHead` → сравнение имени → `ReadTextBody` / рекурсия. Отличаются **имена** вызванных методов (и, для encode, checked/unchecked helper). Рецензент, открыв `{Host}.g.cs`, не должен видеть флаги, enum или комментарии «здесь если CData».

**Как не структурировать**

```
// в ClassSourceProducer.GenerateDeserializeMembers — нельзя
if (_features.HasFlag(XmlFeature.CData) && _features.HasFlag(XmlFeature.Comments))
    emit ReadTextBodyFull(...)
else if (_features.HasFlag(XmlFeature.CData))
    emit ReadTextBodyCData(...)
else if ...
```

```
// в том же методе — нельзя
emit "if (features.HasCData) { ... } else { ... }"
```

```
// можно
emit $"{_binding.ReadTextBody}(cursor, ...)"
```

Producer и без фич содержит ветвления по *типу члена* — они остаются. Новая ось в них не вплетается.

## 5. Контракт рантайма (`XmlScan` / декодер / exhauster)

### 5.1. Выключенная фича — ошибка, а не skip

Иначе `SkipToTag` так и останется «на всякий случай пропускаем `<!`», и выигрыш на DEEP (200 тегов × проверка `rest[1]`) не появится, а контракт «фича выключена» будет ложью.

Примеры default-пути:

- `<!-- x -->` между детьми → исключение (не «пропустить комментарий»).
- `<![CDATA[x]]>` в теле строки → исключение (литеральный `<`).
- `<Foo attr='1'>` → исключение или нераспознанный атрибут (нет двойной кавычки).
- `<Foo attr="1>2">` → голова заканчивается на `>` внутри значения; дальше разбор ломается. Это **приемлемо**: такой документ default не обещает читать. Тест фиксирует «не читаем», а не конкретный текст исключения — текст может меняться.
- `<BaseInfo xmlns:p3="…XMLSchema-instance" p3:type="Derived1">` → не диспатчится в `Derived1`. Без `FlexibleXsiPrefix` нужен `xmlns:xsi` + `xsi:type`.
- строка с `U+0001` на сериализации → **не** бросает `ArgumentException` из `XmlCharGuard` (может получиться не-well-formed XML). Тест это фиксирует.

### 5.2. Разметка: комментарии, PI, DOCTYPE, CDATA

Один флаг `Markup` на первые три и `CData` на четвёртую. Внутри `SkipNonElementMarkup` комментарий, PI и DOCTYPE пропускаются безусловно — на этот метод хост попадает, только если `Markup` включён, — а CDATA отдельным параметром: у неё свой флаг.

Разводить комментарий, PI и DOCTYPE по флагам, как требовала первая редакция этого документа, оказалось нечем оправдать: код у них общий, цена входа одна на всех, а раздельность стоила шести булевых параметров у `ReadHeadMarkup` и пяти у `SkipBodyMarkup` (§17).

`ReadHead` default не принимает и не протаскивает `containsXmlComments` / `containsCDataBlocks`. Мёртвых параметров быть не должно — они уже врали в комментарии к `ReadHead`.

### 5.3. Кавычки в атрибутах — не фича

Голова тега quote-aware всегда: `>` внутри `AttValue` не закрывает тег (XML 1.0 §2.4), значение атрибута читается и в `'`, и в `"`. Отдельного флага под это нет.

В первой редакции это был `QuotedAttributes`, а default искал голову простым `IndexOf('>')` и принимал только двойные кавычки. Замер показал цену quote-aware разбора на уровне шумового порога (~3%, §17), тогда как default без него мог **молча** обрезать голову по `>` внутри значения и не найти `xsi:type`. Дешёвая фича, чья невключённость даёт неверный ответ вместо ошибки, — не фича.

Промежуточных вариантов («только `"`, но без `>` внутри») нет и не предполагается.

### 5.4. `FlexibleXsiPrefix`

Default:

- `GetPreciseNodeType` ищет атрибут с префиксом `xsi` и именем `type`;
- `IsNil` ищет префикс `xsi` и имя `nil` (ужесточение относительно сегодняшнего «любой `nil`»);
- `ReadHead` **не** сканирует атрибуты в поисках xmlns-URI, `XmlnsAttributeName` в default остаётся пустым, если только его не передали снаружи. Наследование префикса по дереву в default не нужно.

Opt-in: текущее поведение, включая наследование найденного префикса детям.

Документы ядра с `p3:type` без флага после задачи **перестают** диспатчиться. Их либо переписывают на `xsi:type`, либо вешают `[XmlFeatures(XmlFeature.FlexibleXsiPrefix)]` (или `SystemXmlCompatible`) на соответствующий тестовый сериализатор. Предпочтительнее **переписать на `xsi`**: это и есть POCO-формат, который пишет генератор (`xmlns:xsi=... xsi:type=...` в `ClassSourceProducer`).

### 5.5. `CharGuard`

`IExhauster.AppendEncoded` сегодня всегда зовёт guard. Ломать интерфейс новой обязательной методой не стоит без нужды.

Рекомендация: вынести экранирование в helper с двумя входами (`Encode` / `EncodeChecked`), генератор в default зовёт encode без guard + `Append`; при флаге — checked. `AppendEncoded` на exhausters оставить как checked-путь (compat, ручные вызовы, кастомные exhausters, которые не трогали). `LengthEstimatorExhauster` не кодирует строку, только считает длину — guard на нём не нужен ни в одном режиме (он и сейчас не зовёт `XmlCharGuard`).

`XmlAttributeEncoder.Encode` сейчас всегда guard-ит. Либо два метода (`Encode` / `EncodeChecked`), либо параметр; генератор выбирает. Поведение «вернуть тот же instance, если экранировать нечего» сохранить на обоих путях.

### 5.6. `CutXmlHead`

Сейчас это общий helper, и его **не** вызывает корневой `Deserialize`. Горячий путь от него не зависит.

Контракт после задачи:

- `CutXmlHead` по-прежнему снимает XML-декларацию и ведущие `S`;
- пропуск `Misc` / `DOCTYPE` после декларации подчиняется **тому же флагу, что у хоста, который helper вызывает**. Helper остаётся общим на сборку, поэтому у него есть перегрузка `CutXmlHead(bool markup, roschar)`, и **сгенерированная** обёртка хоста передаёт туда свой флаг. Вызов `BuiltinCodeHelper.CutXmlHead(span)` без флага = default = только XMLDecl + пробелы.
- Нельзя оставить нынешний «всегда пропускаем PI и DOCTYPE» как единственную перегрузку и звать её из default-хоста: тогда выключенный `Markup` всё равно снимется, и пользователь не поймёт, зачем флаг.

Тесты `SpecComplianceFixture` про stylesheet PI и DOCTYPE в прологе переезжают на хост с `Markup` (или на compat).

### 5.7. `XmlNode2`

Публичный ref-parser, с горячего пути сериализатора уже снят. В рамках задачи:

- либо получает тот же `XmlFeature` (предпочтительно: один контракт на всю библиотеку);
- либо остаётся «полным» XML-подмножеством как сейчас.

Второй вариант проще, но тогда `SpecComplianceFixture` на `XmlNode2` больше не доказывает поведение **сериализатора**. Требование: тесты фич сериализатора гоняют **сгенерированный** `Deserialize`, а не только `XmlNode2`.

`DefaultInjector.Parse(fullNode, …)` через `XmlNode2` — не hot path членов POCO (`ParseBody`). Если `Parse` останется на `XmlNode2`, его фичи должны совпадать с фичами хоста, иначе builtin-корень и член разъедутся. Проще всего, чтобы сгенерированный код для builtin-членов продолжал звать `ParseBody` + `ReadTextBody` с уже выбранной специализацией.

## 6. Поведение compat-слоя

`ClassSourceProducer` для compat-класса вызывается с `XmlFeature.SystemXmlCompatible`. Пользователь **не** пишет атрибут.

Следствия, которые надо покрыть тестами:

- Документ с CDATA, комментариями, `p3:type`, `attr='…'`, `attr="1>2"`, PI/DOCTYPE в прологе (через тот путь, которым compat читает span) читается фасадом так же, как сегодня ядром.
- Native-хост без флагов в том же тесте **не** читает CDATA — доказательство изоляции.
- `IsAccelerated == true` не зависит от флагов: compat всегда «с фичами», отказ по-прежнему только от графа типов / атрибутов BCL, как в [xmlserializer-compat.md](xmlserializer-compat.md).
- Подключение compat не меняет сгенерированный текст native-хоста (инкрементальность + текстовое сравнение в `CompatGeneratorFixture`).

Почему в `SystemXmlCompatible` входит каждый флаг:

| Флаг | Зачем BCL-interop |
|---|---|
| `Comments` | `XmlReader` комментарии пропускает; документы с комментариями `XmlSerializer` читает |
| `CData` | `XmlReader` раскрывает CDATA в текст; руками написанный XML с CDATA BCL примет |
| `ProcessingInstructions` | `XmlReader` PI пропускает |
| `Doctype` | декларация в прологе не мешает BCL (внешние подмножества — отдельная история, её XmlSerDe и сейчас не тянет) |
| `QuotedAttributes` | `XmlReader` принимает `'` и `>` в `AttValue` |
| `FlexibleXsiPrefix` | полноценные xmlns; префикс не обязан быть `xsi` |
| `CharGuard` | `XmlWriter` не выпускает нелегальные Char; compat не должен писать то, чего BCL не напишет |

## 7. Breaking changes и миграция

Native без атрибута после задачи **не** читает то, что читал вчера, если вход пользовался выключенными фичами. Это намеренно.

Миграция потребителя native-пути, которому нужно вчерашнее поведение:

```csharp
[XmlFeatures(XmlFeature.SystemXmlCompatible)]
[XmlSubject(typeof(Order), true)]
public partial class OrderSerializer
{
}
```

Или узкий набор: только `[XmlFeatures(XmlFeature.CData)]`, если вход — чужие CDATA, а префикс уже `xsi`.

README обязан показать оба примера: «быстрый POCO» (без атрибута) и «как раньше / чужой XML».

Внутри репозитория:

- тестовые сериализаторы, которые **проверяют фичу**, получают минимальный набор флагов, а не сразу `SystemXmlCompatible`, чтобы тест не зеленел «потому что включили всё»;
- тестовые сериализаторы, которые проверяют **default POCO**, остаются без атрибута; их XML переписывается на то, что default принимает (`xsi:type`, без CDATA, без комментариев, двойные кавычки);
- `ComplexFixture.AuxXml` сейчас содержит CDATA и `p3:type`. После задачи это **не** вход default-бенчмарка. Разделить: POCO-документ (сериализация `DefaultObject` или вручную без CDATA/`p3`) для default-пути и бенчмарка; старый `AuxXml` — тест opt-in / compat.

## 8. Что менять в коде (ориентир для реализации, не чеклист файлов)

Слой **Common**: enum, атрибут, разведение примитивов `XmlScan` / `XmlTextDecoder` / encoder. Не удалять opt-in реализацию: она нужна флагу и compat.

Слой **Components**: exhausters — checked/unchecked encode. Не заставлять каждого кастомного `IExhauster` реализовывать новую методам, если генератор может звать `Append` после helper.

Слой **Generator**: чтение `[XmlFeatures]` с хоста (OR); compat всегда `SystemXmlCompatible`; `ClassSourceProducer` принимает **готовый** `HostFeatureBinding` (см. §4.5), а не набор флагов, по которому сам ветвится в каждом `Generate*`; выкинуть эвристики из корневого `Deserialize`. Таблица «флаги → binding» — отдельный тип без Roslyn.

Слой **Tests / README / бенчмарки**: §10–§12.

Не смешивать с этой задачей рефакторинг `XmlNode2` off-public, compat-отказы, новые BCL-атрибуты.

## 9. Ограничения реализации

1. **Не runtime-флаг в горячем цикле.** `if (features.HasFlag(CData))` на каждый `<` в `ReadHead` — провал задачи. Специализация на этапе генерации; в рантайме — разные методы или константный generic/`[ConstantExpected]`, который JIT гарантированно сворачивает. Предпочтительны разные методы: это видно в сгенерированном тексте и в тестах генератора.
2. **Не платить за невызванный код на горячем пути.** Методы opt-in могут остаться в `XmlSerDe.Common.dll`; default-хост на них не ссылается.
3. **Выключенное не skip.** См. §5.1.
4. **Compat не заражает native.** См. §3.3.
5. **Сущности остаются.** Выключение `&amp;` не предлагается.
6. **Публичная поверхность `IExhauster` / `IInjector`.** Ломать всех кастомных injectors/exhausters без необходимости нельзя. Добавление метода — ок, если старый сохраняет смысл (checked encode).
7. **netstandard2.0 / net8 / net10.** Специализация не должна жить только под `#if NET8_0_OR_GREATER`. Выигрыш на ns2.0 тоже обязателен (эвристический скан там не дешевле).
8. **Инкрементальность** не регрессирует. См. §4.4 и §10.4.
9. **Генератор не лапша.** `HasFlag` по XML-фичам в `ClassSourceProducer` — только при сборке binding (лучше ни разу: флаги заканчиваются в `HostFeatureBinding.From(XmlFeature)`). Сгенерированный `{Host}.g.cs` не содержит развилок по фичам. Не клонировать сканер по комбинациям флагов. Подробности и запрещённые образцы — §4.5.

## 10. Тесты

Тесты — часть приёмки, не «желательно». Где возможно — существующие фикстуры и `GeneratorHarness` / `CSharpGeneratorDriver`, без нового тестового фреймворка.

Нужны **три семейства** сериализаторов (можно partial-классы рядом с нынешними `XmlSerializerDeserializer*`):

| Семейство | Атрибут | Зачем |
|---|---|---|
| Default | нет | POCO-вход, ошибки на выключенных фичах, бенчмарк |
| Per-flag | ровно один флаг | фича работает; соседняя выключенная — нет |
| Full / Compat | `SystemXmlCompatible` / фасад | паритет с сегодняшним ядром и с BCL |

Нельзя проверять CDATA на классе с `SystemXmlCompatible` как единственное доказательство `CData`: тогда тест не отличит «CDATA включили» от «включили всё».

### 10.1. Поведенческие тесты native default

На сериализаторе **без** `[XmlFeatures]`:

- round-trip обычного POCO (примитивы, список, `xsi:type` с префиксом **`xsi`**, пустые элементы, `xsi:nil`) — зелёный;
- вход с `<!-- … -->` между детьми — исключение;
- вход с `<![CDATA[…]]>` в строковом члене — исключение;
- вход с `<?pi …?>` между детьми — исключение;
- вход с `<!DOCTYPE …>` перед корнем после `CutXmlHead` default — либо `CutXmlHead` не снимает DOCTYPE и `Deserialize` падает, либо падает сам `CutXmlHead` default; не «тихо сняли»;
- атрибут в одинарных кавычках — не читается как сейчас;
- полиморфный член с `xmlns:p3` + `p3:type` — **не** диспатчится в наследника (нужен `xsi`);
- полиморфный член с `xmlns:xsi` + `xsi:type` — диспатчится;
- сериализация строки с `U+0001` — **нет** `ArgumentException` из `XmlCharGuard` (можно не проверять well-formedness выхода);
- сериализация обычной строки с `<>&` — по-прежнему entity-escaping, байт-в-байт как сейчас для легальных Char.

Существующие тесты, которые сегодня зелёные на default-хосте за счёт CDATA / комментариев / `p3` / `>` в атрибуте, **переезжают** (см. §7). Список мест, которые точно затронуты (не исчерпывающий, при реализации пройтись grep):

- `SerDeFixture` — комментарии вокруг `XmlObject10`;
- `CoverageExpansionFixture` / `XmlObject33` — CDATA;
- `ComplexFixture.AuxXml` — CDATA + `p3:type`;
- `SpecComplianceFixture` — `>` в атрибуте, PI, DOCTYPE;
- `SinglePassParserFixture` — `<` внутри CDATA при skip unknown;
- `XmlTextDecoderFixture` — прямые вызовы декодера: оставить как тесты **примитива с CDATA**; отдельно — default-примитив без CDATA.

### 10.2. Поведенческие тесты по одному флагу

Для **каждого** члена `XmlFeature` кроме `None` и составного `SystemXmlCompatible`:

1. Хост с **только этим** флагом принимает документ, который фичу использует, и round-trip/значение совпадает с сегодняшним ядром.
2. Тот же хост **отвергает** документ соседней фичи (матрица ниже).
3. Хост без флага отвергает документ из п.1.

Матрица «включён / чужой документ» (минимум; `+` = принять, `−` = ошибка или не тот смысл):

| Документ → / флаг ↓ | комментарий | CDATA в строке | PI между элементами | DOCTYPE в прологе | `attr='x'` | `attr="1>2"` | `p3:type` | `xsi:type` |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| нет флагов | − | − | − | − | + | + | − | + |
| `Markup` | + | − | + | + | + | + | − | + |
| `CData` | + | + | + | + | + | + | − | + |
| `FlexibleXsiPrefix` | − | − | − | − | + | + | + | + |
| `SystemXmlCompatible` | + | + | + | + | + | + | + | + |

Две колонки с кавычками теперь одинаковы у всех строк: разбор атрибутов quote-aware безусловно (§5.3). Колонки они не потеряли — то, что там стоит `+` уже у default, и есть проверка, что фичи из этого не сделали обратно.

`CharGuard` в эту таблицу не входит: это сериализация. Отдельные тесты:

- с флагом: `U+0001` → `ArgumentException` (как сейчас);
- без флага: не бросает;
- легальные `tab`/`CR`/`LF` в теле при флаге по-прежнему проходят.

Отдельно проверяется, что `Markup` без `CData` **не** снимает строковый член с `IInjector`: обход инжектора — цена именно CDATA (§16, п. 4).

Несколько флагов через OR и через два атрибута — по одному тесту, что поведение совпадает.

### 10.3. Сгенерированный текст (driver)

Через `GeneratorHarness` + `CSharpGeneratorDriver`, по образцу `CompatGeneratorFixture`:

- хост без `[XmlFeatures]`: в порождённом `Deserialize` **нет** идентификаторов `IsXmlCommentExistsHeuristic`, `IsCDataBlockExistsHeuristic`, `CDataHead`, `EnsureValidXmlChars` (или новых имён opt-in-примитивов — тогда в default нет **их** имён). Список запрещённых строк зафиксировать в тесте, чтобы переименование примитива ломало тест, а не молча теряло покрытие;
- хост с `CData`: в тексте есть обращение к CDATA-примитиву, **нет** эвристического `IndexOf` по документу;
- хост с `CharGuard`: есть вызов guard; без флага — нет;
- два хоста в одной компиляции (без флагов и с `CData`) — оба файла порождены, тексты различаются указанным образом;
- компиляция только с `new XmlSerializer(typeof(T))` (compat) и без `[XmlSubject]`: compat-класс содержит opt-in-примитивы, пользовательского `[XmlFeatures]` в исходнике нет.

Отдельно, **без** `CSharpGeneratorDriver`: юнит на таблицу `XmlFeature` → `HostFeatureBinding` (или как она назовётся). На каждый одиночный флаг и на `None` / `SystemXmlCompatible` — ожидаемые имена примитивов. Это и есть защита от лапши: логика выбора call site не спрятана в интерполяциях `ClassSourceProducer` и проверяется без компиляции хоста.

В ревью `ClassSourceProducer`: поиск `HasFlag` / `XmlFeature.` вне ctor/присвоения binding даёт замечание, блокирующее приёмку. Исключение — комментарий, ссылающийся на §4.5.

### 10.4. Инкрементальность

Дополнить `GeneratorIncrementalityFixture`:

- добавление `[XmlFeatures(XmlFeature.CData)]` на хост → выход `Generate` не `Cached`;
- снятие атрибута → снова не `Cached`;
- комментарий в файле хоста при неизменных флагах → `Cached` (уже есть похожий тест — не сломать);
- compat-only правка не меняет native-хост в той же компиляции (если такой сценарий ещё не покрыт).

### 10.5. Compat

`CompatFixture` / `CompatGeneratorFixture`:

- фасад читает CDATA, комментарии, `p3:type`, одинарные кавычки, `>` в атрибуте **без** `[XmlFeatures]` у пользователя;
- `IsAccelerated` по-прежнему true на ускоряемом типе;
- отказ типа (например `HashSet<>`) не зависит от фич;
- native-хост без флагов в том же процессе по-прежнему не читает CDATA.

Дифференциальный `Interop/*` гоняется через compat и/или native с `SystemXmlCompatible`. Default native **не** обязан проходить корпус, где вход — вывод BCL с `<?xml …?>` / xmlns на корне, если эти конструкции требуют флагов или `CutXmlHead`. Не расширять корпус этой задачей; не сужать.

### 10.6. Регрессия уже существующего POCO

Все нынешние тесты round-trip **без** CDATA/комментариев/`p3`/`>` в атрибутах остаются на default-хосте и остаются зелёными. `DeepFixture` — default (в DEEP нет ни одной из opt-in фич). `SerDeFixture` для простых объектов — default после правки XML, где нужно.

`XmlTextDecoderFixture` разделить: поведение с CDATA — тесты opt-in примитива; «нет `&` → `ToString()`» — оба примитива.

`SinglePassParserFixture`: кейс «`<` внутри CDATA не путается с тегом» — только хост с `CData`. Кейс «`>` внутри атрибута при skip unknown» — хост с `QuotedAttributes`. Default-хост получает отдельные тесты на skip unknown **без** этих конструкций.

### 10.7. Негативные тесты генератора

Не требуются диагностики на «странный» набор флагов. Если атрибут повешен не на класс-сериализатор — игнорируется, как прочие атрибуты ядра не на хосте. Отдельный warning не обязателен в этой задаче.

## 11. Бенчмарки

`XmlSerDe.PerformanceTests` после задачи меряет **default-путь** как основной. Иначе README снова будет рассказывать про CDATA-документ и «выключили CDATA — стало быстрее», путая форму документа с формой кода.

Обязательно:

1. **REGULAR default** — XML без CDATA, без комментариев, `xsi:type` (например сериализация `DefaultObject` без XML-декларации, или переписанный `AuxXml`). Это новая база «Deserialize: REGULAR: XmlSerDe».
2. **DEEP default** — как сейчас, фич там нет; число должно улучшиться за счёт снятия эвристик (~4%, порядок из §2).
3. **Serialize default** — без `CharGuard`; ожидается улучшение порядка ~6% на REGULAR.
4. Отдельная категория или фикстура **REGULAR + `SystemXmlCompatible`** на том же объекте / на старом `AuxXml` с CDATA — чтобы в README была таблица «сколько стоит включить всё».
5. Не раздувать `Program.Main` третьим рантаймом. Serialize по-прежнему net10; deserialize — три TFM, как сейчас.

После прогона в README попадают **новые** числа, не копия §2. В тексте — оговорка, что opt-in на том же документе ближе к сегодняшним цифрам, а default — новая база.

Не включать в основной прогон микробенчмарки эвристик: эвристик в generated path больше нет. Если останется публичный `IsXmlCommentExistsHeuristic` для `XmlNode2` — его можно не мерить.

## 13. Критерии приёмки

Работа сделана, если одновременно:

1. Native-хост без `[XmlFeatures]` не сканирует документ эвристиками и не вызывает opt-in-примитивы из §4.1 (доказано тестом сгенерированного текста **и** бенчмарком DEEP/REGULAR default).
2. Каждый флаг из §3.1, кроме составного, имеет тест «только он включён — его документ принимается, соседний нет».
3. `SystemXmlCompatible` на native и compat без пользовательского атрибута принимают матрицу §10.2 целиком.
4. Compat не меняет код native-хоста в той же сборке.
5. `DeepFixture` и POCO round-trip без opt-in-конструкций зелёные на default.
6. README содержит примеры API и таблицу стоимости включённых фич, сверенную с прогоном бенчмарков, а не с оценками §2.
7. Инкрементальность: смена флагов сбрасывает кэш generate; посторонний комментарий — нет.
8. Breaking change описан в README, для вчерашнего поведения есть однострочный рецепт с `SystemXmlCompatible`.
9. Структура генератора по §4.5: таблица флагов тестируется юнитом; `ClassSourceProducer` не ветвится по фичам в `Generate*`; в `{Host}.g.cs` нет лестницы по флагам.

Недостаточно: «добавили bool в `ReadHead` и генератор передаёт `false`». Это текущее состояние, и `SkipToTag` от него не ускоряется.

Недостаточно: «в `GenerateDeserializeMembers` семь `if (HasFlag)`». Поведение может совпасть, приёмка — нет.

## 15. Рекомендуемый порядок работ

Чтобы тесты не краснели «всем сразу» на полмесяца:

1. API: enum + атрибут + чтение в генераторе (пока ещё всегда генерировать старое поведение, если флаг не `None`… нет: лучше сразу развести примитивы, а существующие тестовые хосты временно пометить `SystemXmlCompatible`, чтобы не чинить XML и код одновременно).
2. Развести примитивы `XmlScan` / decoder / encoder и **сразу** ввести `HostFeatureBinding` + один helper вызова на каждый call site (`ReadHead`, `ReadTextBody`, encode). Не «сначала if по флагам в producer, потом вынесем». Все нынешние `[XmlSubject]` в `XmlSerDe.Tests` на этом шаге получают `[XmlFeatures(XmlFeature.SystemXmlCompatible)]` — регрессия поведения нулевая.
3. Compat: передавать `SystemXmlCompatible` явно (даже если тестовые хосты уже с атрибутом). Тест «атрибут не нужен».
4. Снять `SystemXmlCompatible` с тех тестовых хостов, которым фичи не нужны; поправить их XML на `xsi` / без CDATA. Добавить per-flag хосты и матрицу §10.2.
5. Выкинуть эвристики из generated `Deserialize`. Проверить инкрементальность и driver-тесты текста.
6. Бенчмарки + README + таблица стоимости.
7. Пройти критерии §13.

Шаг 2 с временным `SystemXmlCompatible` на тестах — допустимый промежуточный коммит; в мерже его на default-хостах быть не должно.

## 16. Расхождения с этим документом

Реализация следует §3–§5 и §9. Ниже — места, где выбранный код не совпадает с формулировкой, но наблюдаемое поведение совпадает.

1. **Markup-флаги в `.g.cs` — булевы константы, не `XmlFeature`.** Разметочный хост вызывает `XmlScan.ReadHeadMarkup(cdata, flexibleXsi, …)` (и аналогично `ReadTextBodyMarkup` / `SkipBodyMarkup`). Это не лестница `if (features.HasFlag)` в сгенерированном тексте: литералы сворачиваются. Отдельного клона сканера на комбинацию флагов нет.
2. **`XmlNode2` остаётся полным подмножеством** (quote-aware голова, CDATA, гибкий `xsi`). Сгенерированный hot path его не зовёт. Ускорять публичный `XmlNode2` документ разрешал не делать.
3. **`CutXmlHead` — bool-перегрузка плюс сгенерированная обёртка.** Общий `BuiltinCodeHelper.CutXmlHead(bool markup, span)` остаётся, но каждый хост получает свой `CutXmlHead(span)`, который подставляет собственный флаг (§5.6). Безаргументный общий helper по-прежнему снимает только XMLDecl и пробелы.
4. **`IsNil` без `FlexibleXsiPrefix` — `XmlHead.IsXsiNil`** (литерал `xsi:nil`), не любой атрибут `nil`.
5. **Таблица стоимости в README** — in-process probe на `XmlObject2` (`--feature-cost`), не полный прогон BenchmarkDotNet. Probe гоняет все случаи round-robin по пять раундов и берёт минимум: при замере строго по порядку первый случай впитывал прогрев общего кода, и таблица врала в разы. Официальные REGULAR/DEEP таблицы помечены как снимок *до* opt-in; в матрицу добавлена категория `REGULAR_COMPAT`.
6. **`ClassSourceProducer` не ветвится по флагам в `Generate*`.** Флаги заканчиваются в `HostFeatureBinding.From` и в ctor (`ReadXmlFeatures` / `XmlFeature.SystemXmlCompatible` для compat). Исключение по §4.5: комментарий со ссылкой на этот документ и присвоение `_binding`.
7. **`CharGuard` выключается снятием проверки, а не сменой способа записи.** У `IExhauster` появилась пара `AppendEncodedUnchecked` / `AppendAttributeEncodedUnchecked`; default зовёт её, а не `Append(XmlTextEncoder.Encode(...))`, как предлагал §5.5. Причина — замер: `Encode` при наличии экранируемого символа строит промежуточную строку, и default-сериализация REGULAR выходила медленнее и с 864 B/оп против нуля у пути с флагом. Заодно совпадает обработка `null`: элемент коллекции `null` пишется пустым элементом при любом наборе фич, а не роняет `ArgumentNullException` только у default-хоста.
8. **Строковый член снимается с `IInjector` только при `CData`.** Без этого флага генератор по-прежнему пишет `inj.ParseBody(text, out string …)`: у `IInjector` нет CDATA-перегрузки, но фича, которую не включали, не должна выбрасывать пользовательский инжектор из разбора. С `CData` хост зовёт `XmlTextDecoder.DecodeElementTextWithCData` напрямую — единственный случай обхода инжектора.
9. **Default-перегрузки `ReadHead` — отдельные тела, а не один core с булевыми параметрами.** §9.1 требует, чтобы специализация доходила до JIT; общий core оказывался слишком велик для инлайна, и константы вызывающей стороны становились обычными аргументами. `ReadTextBody` разведён так же. Разметочные варианты булевы параметры сохраняют: разметка — не POCO-hot-path (§4.5). После §17 таких default-тел два (`ReadHead`, `ReadHeadFlexibleXsi`), а не четыре.
10. ~~**`GetPreciseNodeType` / `IsNil` выбираются по двум осям.**~~ Отменено в §17: кавычки перестали быть осью, у пары type/nil снова два варианта (`GetXsiType` / `GetPreciseNodeType`, `IsXsiNil` / `IsNil`), и оба quote-aware.
11. **`DecodeElementText` без CDATA ищет `&` и `<` одним `IndexOfAny`.** Раздельные `IndexOf('&')` и `IndexOf('<')` давали два прохода на быстром выходе и полный доскан остатка на каждой сущности внутри цикла — O(k·n); default-декодер выходил вдвое медленнее CDATA-варианта на строке с 80 сущностями.

## 17. Свёртка набора флагов после замера

Первая редакция этого документа завела семь флагов и запретила их объединять (§3.1). Реализация была сделана именно так, после чего лестница `FeatureLadderHosts` + `--feature-cost` дала цену каждого флага на одном документе (REGULAR, медиана трёх прогонов, шумовой порог ~3%):

| Флаг | Десериализация | Сериализация |
|---|---:|---:|
| `Comments` | 1.14× | 1.00× |
| `CData` | 1.10× | 1.00× |
| `ProcessingInstructions` | 1.07× | 1.00× |
| `Doctype` | 1.08× | 1.00× |
| `QuotedAttributes` | **1.03×** | 1.00× |
| `FlexibleXsiPrefix` | 1.07× | 1.00× |
| `CharGuard` | 1.00× | 1.15× |

Накопительно первые четыре давали +14%, +2%, ~0, +1%: цена не у конструкции, а у входа на разметочный путь. Из этого сделаны два вывода.

**`QuotedAttributes` удалён, поведение стало умолчанием.** Единственный флаг, чья изолированная цена лежала на шумовом пороге, и при этом единственный, чьё отсутствие давало не ошибку, а **молча неверный** разбор: голова обрезалась по первому `>`, в том числе по `>` внутри `AttValue`, и `xsi:type` мог не найтись. Удаление убрало из `XmlScan` метод `FindFirstGt`, параметр `quoted` у `ScanHeadCore` / `ParseAttributeCore` / `SkipBodyCore`, обёртки `ScanHeadQuoted` / `ParseAttributeQuoted` / `SkipBodyQuoted`, два из четырёх default-тел `ReadHead` и четыре из восьми акцессоров `XmlHead` (пара type/nil снова стала выбираться по одной оси, а не по двум — п. 10 §16 больше не действует).

**`Comments`, `ProcessingInstructions`, `Doctype` свёрнуты в `Markup`, `CData` включает его в себя.** Раздельность покупала только строгость вида «комментарии да, DOCTYPE нет», которой никто не просил, а стоила шести булевых параметров у `ReadHeadMarkup`, пяти у `SkipBodyMarkup`, двух у `ReadTextBodyMarkup`, трёх у `CutXmlHead`, вспомогательного `MarkupFeatures` и трёх гейт-бросков в `SkipNonElementMarkup`. Всё это удалено; в `HostFeatureBinding` от механизма `*PrefixArgs` остался один `cdata`.

`CData` осталась отдельным членом, потому что у неё есть цена помимо входа: свой декодер и обход `IInjector` для строк (§16, п. 8). Хост с `Markup`, но без `CData`, инжектор не обходит.

Итоговая цена, замеренная тем же способом после свёртки:

| Шаг | Десер. ×base | Δ | Сер. ×base | Δ |
|---|---:|---:|---:|---:|
| default | 1.00 | — | 1.00 | — |
| `+ Markup` | 1.15× | +15% | 1.00× | — |
| `+ CData` | 1.16× | ~0 | 1.00× | — |
| `+ FlexibleXsiPrefix` | 1.28× | +11% | 1.00× | — |
| `+ CharGuard` = `SystemXmlCompatible` | 1.27× | ~0 | 1.17× | +17% |

Три цены — три флага (плюс `CData` со своей четвёртой). Что потеряно и принято сознательно:

1. Нельзя сказать «комментарии принимаю, DOCTYPE нет» — ломающее изменение для того, кто на такую строгость опирался.
2. Хост с `CData` теперь принимает и комментарии/PI/DOCTYPE, поскольку `CData` включает `Markup`.
3. Default стал медленнее примерно на ту самую цену `QuotedAttributes` (~3%) — в обмен на то, что перестал молча неправильно читать легальный XML.
4. `XmlFeature` — публичный enum: удалённые и переименованные члены ломают исходную совместимость у всех хостов. Смысл `SystemXmlCompatible` не изменился.
